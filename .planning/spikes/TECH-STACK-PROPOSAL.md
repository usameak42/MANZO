# Tech Stack Proposal — Winamp macOS Port

**Constraints:**
- Apple Silicon (ARM64) with SIMD optimization
- macOS native translucency
- yt-dlp bundled as sidecar binary
- Heavy Winamp-style skeuomorphic UI

**Informed by:** Spikes 001–004 (DSP interface, EQ math, MP3 pipeline, playback chain)

---

## Option A — Swift + AVFoundation + Accelerate

### Rationale
Leans entirely on Apple's own stack. AVAudioEngine replaces the output plugin layer
(`Out_Module::Write` → `AVAudioPlayerNode.scheduleBuffer`). Accelerate's `vDSP_biquad`
is a hardware-accelerated ARM NEON biquad that directly maps the `eq10dsp.cpp` inner loop.
AppKit gives pixel-level control for skeuomorphic chrome.

### Audio / DSP
- **Decoder**: `AVAudioFile` or `AVAudioConverter` for MP3 (wraps AudioToolbox/CoreAudio).
  For low-level gapless control (529-sample delay trimming), use `ExtAudioFileRef` + 
  `kAudioConverterDecompressionMagicCookie`, or bundle libmpg123 as a static lib.
- **EQ**: Port `eq10dsp.cpp` to Swift using `vDSP_biquad` / `vDSP_biquadm`.
  The dual-biquad structure maps to two `vDSP_biquad_Setup` instances per band.
  Double-precision coefficients fit `vDSP_biquadD`.
- **Pipeline**: `AVAudioEngine` graph: source node → mixer (volume/pan) → EQ tap → output.

### UI
- **AppKit + Core Animation** for the skeuomorphic window chrome (exact pixel placement).
- `NSVisualEffectView` (`.behindWindow` / `.withinWindow` blending) for translucency.
- Custom `CALayer` with `NSImage`-backed skin bitmaps for classic Winamp look.
- Or **SwiftUI + Canvas** for the spectrum analyzer / VU meter redraws.

### yt-dlp Packaging
- Bundle `yt-dlp` binary at `MyApp.app/Contents/MacOS/yt-dlp` (or `Resources/`).
- Invoke via `Process()` (`Foundation`): `process.executableURL = Bundle.main.url(forResource:...)`.
- Parse stdout with `Pipe` → `AsyncBytes`.

### Pros
- Single language, single build system (Xcode / Swift Package Manager)
- `vDSP_biquad` is NEON-vectorized automatically; zero hand-written SIMD
- Native `NSVisualEffectView` translucency — no custom compositing
- AppKit gives exact pixel control for skeuomorphic fidelity
- Smallest binary, fastest sandbox approval path

### Cons
- AVFoundation MP3 decoder delay trimming is opaque — harder to achieve true gapless
- No DSP plugin extensibility (no Win32 DLLs); would need AUv3 wrapper to expose plugin slot
- vDSP biquad is less flexible for custom filter topologies (e.g. future Linkwitz-Riley crossovers)

### Performance
- `vDSP_biquadm` processes 10 bands across N channels in a single vectorized pass
- ARM NEON used automatically by Accelerate; no `arm_neon.h` required
- Estimated EQ overhead: < 0.3 ms per 1024-sample buffer at 44100 Hz on M1

## Option B — Rust (audio/DSP core) + Swift/AppKit (UI) via FFI  ★ Recommended

### Rationale
Rust handles the entire audio pipeline (decode → EQ → output) with zero-cost abstractions
and safe concurrency. The biquad math from `eq10dsp.cpp` is a direct 1:1 port (~150 lines).
ARM NEON SIMD is explicit and portable. Swift owns the UI layer, calling into Rust via
`swift-bridge` or a plain C header. This is the architecture that gives maximum DSP
performance while keeping the UI idiomatic macOS.

### Audio / DSP
- **Decoder**: `mpg123` Rust binding (`mpg123-sys` crate) preserving the streaming feed API
  (`mpg123_open_feed` + `mpg123_feed` + `mpg123_read`). Decoder delay (529 samples)
  tracked and trimmed in Rust for gapless. Or `minimp3` (single-file, MIT, no C dep).
- **EQ**: Port `eq10dsp.cpp` directly to Rust. The inner loop:
  ```rust
  let y0 = (x - x2) * a0 + y1 * b1 + y2 * b2 + 1e-30_f64; // denormal fix
  out = (y0 + x) as f32;
  ```
  With `std::arch::aarch64::*` NEON intrinsics for the inner loop, or `wide` / `packed_simd2`
  crates for portable SIMD across x86/ARM.
- **Output**: `coreaudio-rs` or `cpal` (cross-platform audio I/O, wraps CoreAudio on macOS).
  `cpal` output callback maps directly to the `Out_Module::Write` ≤8192-byte non-blocking model.
- **Pipeline**: Rust `Arc<Mutex<>>` or `crossbeam::channel` between decode thread and output callback.

### UI
- **AppKit** via Swift, calling Rust core through a C-compatible header generated by `swift-bridge`
  or manually (`extern "C" fn`).
- `NSVisualEffectView` for translucency.
- Skin bitmaps loaded as `NSImage`; custom `NSView.draw(_:)` for pixel-perfect Winamp chrome.

### yt-dlp Packaging
- Rust `std::process::Command::new("./yt-dlp")` with path resolved via
  `std::env::current_exe().parent()`.
- Stdout streamed via `BufReader` lines → async channel to UI.

### Pros
- Most direct port of DSP math — `eq10dsp.cpp` translates line-for-line to safe Rust
- Full control over ARM NEON SIMD (`vst1q_f32`, `vld1q_f32`, `vmlaq_f32` for IIR inner loop)
- Safe concurrency for decode/EQ/output threads — no data races
- mpg123 is already ARM64-ready; decoder delay preserved precisely
- Rust's ownership model prevents the class of buffer-overrun bugs common in audio code

### Cons
- Two build systems: Cargo + Xcode (manageable with `build.rs` + `xcode-build-settings`)
- Swift-Rust FFI adds ~1 day of bridging setup (`cbindgen` for C headers)
- Larger binary than pure Swift (Rust stdlib statically linked, ~2–4 MB overhead)
- No AUv3 plugin slot without additional wrapping

### Performance
- Manual NEON: process 4 floats/cycle in the IIR inner loop
- EQ overhead: < 0.1 ms per 1024 samples on M1 with NEON unrolling
- Zero-copy decode→EQ path if `mpg123` writes directly into the EQ input buffer

## Option C — C++23 (DSP core) + SwiftUI (thin UI wrapper)

### Rationale
The most conservative port. The EQ and decode code barely changes — `eq10dsp.cpp` compiles
as-is on ARM64 Clang with `-O3 -march=armv8-a`. Swift wraps the C++ core via
Objective-C++ (`*.mm` bridge files). Highest risk is the skeuomorphic UI: building
it in SwiftUI/AppKit from Objective-C++ is verbose but well-trodden.

### Audio / DSP
- **Decoder**: `libmpg123` linked directly (CMake `find_package(mpg123)`). Feed/read API preserved.
- **EQ**: `eq10dsp.cpp` compiled with `-O3 -ffast-math`. ARM NEON via `<arm_neon.h>`:
  the inner IIR loop can be manually unrolled with `vmlaq_f32` for 4× throughput.
- **Output**: `CoreAudio AudioQueue` C API or `AudioUnit` render callback.
  Replace `Out_Module::Write(char*, ≤8192)` with `AudioQueueBufferRef` fill + enqueue.
- **Volume/Pan**: `AudioQueueSetParameter(kAudioQueueParam_Volume)`.

### UI
- **SwiftUI** for app shell, window chrome, preferences.
- Custom `NSView` subclass in Objective-C++ (`WinampSkinView.mm`) for the skeuomorphic
  bitmap skin rendering — direct `NSImage` + `NSBezierPath` compositing.
- `NSVisualEffectView` for translucency (same as Option A/B).

### yt-dlp Packaging
- `posix_spawn` or `NSTask` from Objective-C++ bridge.
- Binary at `Contents/MacOS/yt-dlp`.

### Pros
- Nearest to a straight compile — `eq10dsp.cpp` unchanged, mpg123 unchanged
- Lowest DSP rewrite risk (exact numerical behavior preserved)
- ARM64 auto-vectorization often matches manual NEON for simple loops
- C++ AudioUnit render callbacks are the lowest-latency macOS output path

### Cons
- Objective-C++ bridge (`*.mm`) is arcane and error-prone at scale
- `cmake` + Xcode dual build system is messier than Cargo + Xcode
- C++ memory management in audio threads requires careful discipline
- SwiftUI + Obj-C++ interop for complex custom views has known pain points
- Harder to make safe/testable: no borrow checker, manual lifetime management in audio callbacks

### Performance
- Clang `-O3 -march=armv8-a+simd` auto-vectorizes the IIR loop adequately
- `AudioUnit` render callback is the lowest-latency CoreAudio path (~5 ms buffer achievable)
- libmpg123 has assembly-optimized paths for ARM; links from Homebrew or vcpkg

## Recommendation Matrix

| Criterion | Option A (Swift) | Option B (Rust+Swift) ★ | Option C (C++) |
|-----------|-----------------|------------------------|----------------|
| EQ port fidelity | Medium (vDSP abstraction) | High (direct translation) | Highest (copy-paste) |
| SIMD control | Low (auto via Accelerate) | High (explicit NEON) | Medium (auto-vec + manual) |
| macOS translucency | Native | Native (Swift UI layer) | Native |
| Concurrency safety | Medium (actors) | High (ownership) | Low (manual) |
| Build complexity | Low | Medium | Medium-High |
| Skeuomorphic UI | Medium | Medium | Medium |
| yt-dlp integration | Trivial | Trivial | Trivial |
| Gapless accuracy | Low (opaque decoder) | High (explicit delay trim) | High (explicit delay trim) |

**Recommended: Option B.** The Rust core gives a direct, safe, verifiable port of
the `eq10dsp.cpp` math with the most DSP correctness guarantee. The Swift UI layer
is idiomatic and keeps skin rendering clean. The FFI surface is small (~10 functions:
open/close/play/pause/seek/setEQ/setVolume/setGain).

## yt-dlp Sidecar — Universal Notes (all options)

1. Bundle at `MyApp.app/Contents/MacOS/yt-dlp` (pre-built universal binary from yt-dlp releases).
2. Strip quarantine on first launch: `xattr -d com.apple.quarantine <path>` via `xpc_connection`
   or request Hardened Runtime entitlement `com.apple.security.cs.allow-unsigned-executable-memory`.
3. Recommended invocation pattern:
   ```
   yt-dlp -x --audio-format mp3 -o - <URL>  |  [audio pipeline stdin]
   ```
   Pipe stdout directly into the decode buffer — zero temp-file writes.
4. Version-lock: ship a specific yt-dlp version in the bundle; add update check on launch.
