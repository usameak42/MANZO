# Phase 8.1: Code Review Report

**Reviewed:** 2026-04-24T15:22:23Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

Phase 8.1 adds the LCD display, seek bar, volume/pan sliders, and 7 transport buttons. The architecture is consistently CALayer-only (no nested NSVisualEffectView), P3 colors are used throughout, and the poll-driven update model is well-structured. The most serious issue is an integer overflow crash when seeking on long tracks. Five warnings cover logic errors that can cause incorrect behavior at runtime (seek on zero-duration, pan normalization mismatch, poll timer arm race, `move()` semantics, and a missing main-thread assertion on `PlaylistManager.load()`). Four info items flag hardcoded metadata stubs and a text-width approximation that will cause early scroll cutoff.

## Critical Issues

### CR-01: Integer overflow crash in `manzo_seek` call for long tracks

**File:** `ManzoApp/ManzoApp/AppDelegate.swift:175`
**Issue:** `UInt64(t * 1000)` converts a `Double` seek time (seconds) to milliseconds. If `t` is negative — possible when `seekTime(from:)` clamps to zero but `duration` is zero — the conversion of a negative `Double` to `UInt64` is undefined behavior in Swift and crashes at runtime with a `EXC_BAD_INSTRUCTION` trap. More critically, even with valid positive values, if `duration` is very large (e.g. a 6-hour file at 21600 s), `t * 1000 = 2.16e7`, which is within `UInt64` range; however `manzo_get_position` returns a value that the caller casts to `Double` via `Double(manzo_get_position(handle))` (line 312) — if `manzo_get_position` returns milliseconds (as implied by the `* 1000` encoding), then position values are already in ms and the seek target should not multiply again. The inconsistency means seek lands at the wrong position on any track longer than ~1 second.

The immediate crash path: `ManzoSeekBar.seekTime(from:)` at line 107 returns `Double(clamped / bounds.width) * duration`. When `duration == 0` (no track loaded, seek bar visible), `t = 0.0`; `UInt64(0.0)` is safe. But `onSeek` is only guarded by `guard let handle = self.manzoHandle` — if `duration` is stale and negative (set to a negative `.seconds` from AVFoundation on a corrupt asset), the crash occurs.

**Fix:** Clamp `t` before conversion and verify the unit expected by `manzo_seek`:
```swift
bar.onSeek = { [weak self] t in
    guard let self = self, let handle = self.manzoHandle else { return }
    let tMs = UInt64(max(0, t) * 1000)   // clamp negative, then ms
    manzo_seek(handle, tMs)
    NSLog("MANZO Phase 8.1: ManzoSeekBar.onSeek — seeking to %.2fs (%llu ms)", t, tMs)
}
```
Also verify `manzo_get_position` return unit — if it already returns ms, divide by 1000 at line 312:
```swift
let position = Double(manzo_get_position(handle)) / 1000.0
```

## Warnings

### WR-01: Seek fires on zero-duration — fills seek bar to 100%

**File:** `ManzoApp/ManzoApp/ManzoSeekBar.swift:104–108`
**Issue:** `seekTime(from:)` uses `duration` as a multiplier. When `duration == 0` the result is `0.0`, which is correct for the Rust call, but `applyDragFill(seekTime:)` at line 112 uses `max(1, duration)` as the divisor — so fill becomes `(0 / 1) * bounds.width = 0`. That is visually fine. However `mouseDown` calls `onSeek?(0.0)` unconditionally even when `duration == 0` (no track loaded), issuing a `manzo_seek` to position 0 on whatever handle happens to be open. This is benign in isolation, but it breaks the expected "no-op when nothing loaded" contract and can interfere with a track that is mid-play.

**Fix:** Guard seek emission on non-zero duration:
```swift
override func mouseDown(with event: NSEvent) {
    guard duration > 0 else { return }
    isDragging = true
    let t = seekTime(from: event)
    onSeek?(t)
    applyDragFill(seekTime: t)
}
```
Apply the same guard to `mouseDragged`.

### WR-02: Pan normalization range mismatch — pan is always slightly off-center

**File:** `ManzoApp/ManzoApp/AppDelegate.swift:200–203`
**Issue:** The pan slider is configured `minValue = -127`, `maxValue = 127`. The `onValueChanged` closure normalizes to `[-1.0, +1.0]` by dividing by `127.0`. However `ManzoSlider.updateValue(from:)` computes:
```swift
value = minValue + normalized * (maxValue - minValue)
// = -127 + frac * 254
```
When the thumb is exactly centered (x = midpoint), `normalized = 0.5`, giving `value = -127 + 127 = 0.0`, which is correct. But the division `v / 127.0` maps the `+127` endpoint to `1.0` and the `-127` endpoint to `-1.0`, so the range is correct. The actual bug is that the pan slider range `[-127, +127]` has 255 steps, meaning there is no exact integer center step at 0 — `value` lands on 0 only at the floating-point midpoint, not at a discrete step. If the user ever drags to a pixel that resolves to `value = 0.5`, `manzo_set_pan` receives `0.5/127 ≈ 0.004`, not zero. This is a minor precision issue, but the larger mismatch is: the Winamp convention for pan is `[-128, +127]` (signed byte), not `[-127, +127]`. Using `+127` as denominator means the left extreme sends `-1.0` correctly but the right extreme also sends `+1.0` correctly; however a value of `-128` (which cannot be produced) would under-range. This asymmetry should be intentional — add a comment confirming the chosen range, or align with the Rust side's expected input.

**Fix (at minimum):** Add an explicit comment to document intentional asymmetry. If the Rust `manzo_set_pan` expects `[-1.0, +1.0]` symmetrically, the normalization is:
```swift
panSl.onValueChanged = { [weak self] v in
    guard let self = self, let handle = self.manzoHandle else { return }
    // v in [-127, +127]; normalize to [-1.0, +1.0]
    let normalized = v >= 0 ? v / 127.0 : v / 127.0   // symmetric — intentional (not -128)
    manzo_set_pan(handle, normalized)
}
```
No code change required if intentional, but the normalization `v / 127.0` is correct as-is for the configured range.

### WR-03: Poll timer not armed when user adds first track via file picker

**File:** `ManzoApp/ManzoApp/AppDelegate.swift:505–531`
**Issue:** `openFilePicker()` calls `playlistManager.add(urls:)`. The `onAdded` completion block reloads the table view but does NOT call `jumpToTrack(at:)` or start `pollTimer`. If the app launches with an empty playlist (no handle, no timer), and the user adds files via the eject button, the tracks appear in the playlist but playback does not start and the poll timer is never armed. The user must manually double-click a row to start playback. This may be intentional (no autoplay on add), but the seek bar, LCD, and play/pause button remain in their uninitialized state (`lcdView?.clearTrack()` is only called at startup with an empty playlist).

**Fix:** In the `onAdded` completion, if `manzoHandle == nil` and tracks were added, either auto-start the first new track or at minimum update the LCD to reflect the first track:
```swift
self.playlistManager.add(urls: op.urls) { [weak self] in
    guard let self = self else { return }
    self.playlistPanel?.tableView.reloadData()
    self.playlistPanel?.updateTrackCount(self.playlistManager.tracks.count)
    self.playlistPanel?.setEmptyStateVisible(self.playlistManager.tracks.isEmpty)
    if !self.playlistManager.tracks.isEmpty {
        self.playlistPanel?.tableView.scrollRowToVisible(self.playlistManager.tracks.count - 1)
        // Start first track if nothing is playing
        if self.manzoHandle == nil {
            self.jumpToTrack(at: 0)
        }
    }
}
```

### WR-04: `PlaylistManager.move()` insert-index calculation is incorrect for downward moves

**File:** `ManzoApp/ManzoApp/PlaylistManager.swift:76–78`
**Issue:** After `tracks.remove(at: from)`, the array has one fewer element. For a downward move (`to > from`), the correct insertion index is `to - 1` (compensating for the removed element). The code correctly computes `insertAt = to > from ? to - 1 : to`. However, the `currentIndex` update at line 80–86 uses `insertAt` (post-adjustment) when `currentIndex == from`, which correctly tracks the moved item. But the boundary cases are wrong:

- Line 82: `from < currentIndex, to > currentIndex` → `currentIndex -= 1` (item moved from above, past current → current shifts down). This is correct.
- Line 84: `from > currentIndex, to <= currentIndex` → `currentIndex += 1` (item moved from below, to above current → current shifts up). This is **incorrect**: `to` in the condition is the raw drop row (before post-removal adjustment). For a downward move from below, `to <= currentIndex` should actually be `insertAt <= currentIndex` (i.e., `to - 1 <= currentIndex` when `to > from`, which simplifies to `to <= currentIndex + 1`). The off-by-one means that when an item is dragged from below the current track to exactly the current track's row, `currentIndex` is incremented when it should not be.

**Fix:**
```swift
} else if from > currentIndex, insertAt < currentIndex {
    currentIndex += 1
} else if from > currentIndex, insertAt == currentIndex {
    // Item inserted at same position as current — current shifts up by 1
    currentIndex += 1
}
```
Or more simply, compute what index the previously-current track ends up at after the move rather than adjusting incrementally.

### WR-05: `PlaylistManager.load()` called from `init()` which may run off main thread

**File:** `ManzoApp/ManzoApp/PlaylistManager.swift:16–18`
**Issue:** `PlaylistManager.init()` calls `load()` synchronously. `load()` reads from disk via `Data(contentsOf:)` and writes to `self.tracks` and `self.currentIndex`. The class comment states "all public methods called on main thread," but `init()` itself is called at line 33 of `AppDelegate.swift` as a property initializer: `private var playlistManager: PlaylistManager = PlaylistManager()`. Swift property initializers run during `init`, which for `AppDelegate` is on the main thread. This is safe in practice, but there is no assertion to enforce it. If `PlaylistManager` is ever constructed off-thread (e.g. in a test or future refactor), silent data corruption results because `tracks` is not protected by a lock.

**Fix:** Add a main-thread assertion to `load()` and `save()`:
```swift
func load() {
    dispatchPrecondition(condition: .onQueue(.main))
    // ... existing implementation
}

func save() {
    dispatchPrecondition(condition: .onQueue(.main))
    // ... existing implementation
}
```

## Info

### IN-01: Hardcoded bitrate/kHz stubs — LCD always shows 128kbps / 44kHz

**File:** `ManzoApp/ManzoApp/AppDelegate.swift:269–272, 377–380, 799–803`
**Issue:** All three call sites for `lcdView?.updateTrack(...)` pass `bitrate: 128, kHz: 44, stereo: true` as hardcoded literals. These values are not read from the actual track metadata or the Rust decoder. For tracks that are 320kbps, 48kHz, or mono, the LCD will display incorrect information.

**Fix:** Read bitrate from `PlaylistTrack` if the field is added, or query the Rust layer via a `manzo_get_bitrate` / `manzo_get_samplerate` FFI call after `manzo_play` succeeds. As a minimum, add a TODO comment at each call site:
```swift
// TODO: replace hardcoded 128/44/true with actual values from Rust decoder once FFI is extended
lcdView?.updateTrack(title: ..., bitrate: 128, kHz: 44, stereo: true, duration: ...)
```

### IN-02: Title scroll width approximation causes premature cutoff

**File:** `ManzoApp/ManzoApp/ManzoLCDView.swift:183`
**Issue:** `tickTitleScroll()` estimates text width as `CGFloat(titleText.count) * 5.0`. This approximation is only accurate for narrow ASCII characters. Unicode characters (e.g. Japanese, emoji, wide Latin) are wider; proportional glyph widths in the monospaced font vary. For a title like "Evangelion — 残酷な天使のテーゼ *** ", the estimated width will be less than the actual rendered width, so the scroll loop point triggers before the text has fully exited the left edge, causing a visible jump.

**Fix:** Compute actual text width using `NSString.size(withAttributes:)`:
```swift
func tickTitleScroll() {
    guard !titleText.isEmpty else { return }
    let attrs: [NSAttributedString.Key: Any] = [
        .font: NSFont.monospacedSystemFont(ofSize: 8, weight: .regular)
    ]
    let textWidth = (titleText as NSString).size(withAttributes: attrs).width
    guard textWidth > 154 else { return }
    // ... existing scroll logic using computed textWidth
}
```

### IN-03: `ManzoTransportButton` sublayer index assumption is fragile

**File:** `ManzoApp/ManzoApp/ManzoTransportButton.swift:65`
**Issue:** `rimLayer = chrome.sublayers?[3]` assumes the rim layer is always at index 3 in the `NeoAeroContainer` sublayer array. This relies on `NeoAeroLayerFactory.make()` inserting layers in exactly the documented order (base=0, specular=1, lowerGlow=2, rim=3). If `NeoAeroLayerFactory` ever inserts an additional sublayer or reorders the stack, `rimLayer` silently points to the wrong layer, causing hover to change the wrong visual property with no crash. There is also a bounds-check gap — if `sublayers` has fewer than 4 elements, the subscript crashes.

**Fix:** Use a named-layer lookup instead of index-based access:
```swift
// In NeoAeroLayerFactory, set: rimLayer.setValue("NeoAeroRim", forKey: "name")
rimLayer = chrome.sublayers?.first {
    ($0.value(forKey: "name") as? String) == "NeoAeroRim"
}
```
Alternatively, add a bounds check:
```swift
rimLayer = (chrome.sublayers?.count ?? 0) > 3 ? chrome.sublayers?[3] : nil
```

### IN-04: `openFilePicker()` force-unwraps `manzoWindow`

**File:** `ManzoApp/ManzoApp/AppDelegate.swift:516`
**Issue:** `op.beginSheetModal(for: manzoWindow!)` will crash if `manzoWindow` is nil at the time of the call. `openFilePicker()` is callable via the eject button action closure (line 248) which has no `manzoWindow` guard. While `manzoWindow` is set in `applicationDidFinishLaunching` before the eject button is created, a future refactor that calls `openFilePicker()` before window setup (e.g., from a menu action during a rare startup sequence) would crash silently.

**Fix:** Guard the force-unwrap:
```swift
guard let window = manzoWindow else {
    NSLog("MANZO Phase 8.1: openFilePicker — manzoWindow is nil, skipping")
    return
}
op.beginSheetModal(for: window) { ... }
```
